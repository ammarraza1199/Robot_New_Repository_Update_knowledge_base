# A Simple Guide to Updating and Maintaining Your Secure Robot

This document explains how we manage and update our Hospital Assistant Robot, especially focusing on how we give it new "instructions" (code updates) or check its internal "health" and data. Our robot is designed to be very secure, which means we have a special, careful way of making changes.

---

## 1. Why We Can't Just "Change Things" on the Robot Directly (The Secure Wall)

Imagine your robot's main "brain" or "instruction manual" is stored inside a **very secure, locked safe**. Not only is it locked, but the instructions inside are also written in a **secret code** (encrypted). Only your robot knows the secret to read these instructions, and it keeps them locked away.

*   **Locked Safe (Read-Only Code):** When the robot is running, it only has "read-only" access to its instructions. This means it can *read* them to know what to do, but it *cannot change them*. This is like having a DVD movie: you can watch it, but you can't re-record over it.
*   **Secret Code (Encrypted):** Even if someone were to sneak a peek at the safe, the instructions inside would look like gibberish because they're in a secret code. Only the robot itself, when it's starting up on *its specific hardware*, knows how to decipher them.

**Why is it so secure?** This system protects the robot from accidental changes, viruses, or anyone trying to tamper with its core functions. It ensures the robot always follows the approved, verified instructions.

---

## 2. How to Give the Robot New Instructions (Code Updates/Fixes - The "New Recipe" Process)

Think of giving the robot new instructions like a **chef getting a new recipe for a special dish.** The chef doesn't change the dish *while it's cooking*. Instead, they get a new, improved recipe, understand it, and then prepare the dish again with the new instructions.

Here’s our step-by-step process for updating the robot:

*   **Step 1: Tell the Robot to Pause (Stop Services)**
    *   **Explanation:** Before we can update its "recipe book," we need to tell the robot to temporarily stop all its current tasks. It's like hitting a "pause" button on its operations.
    *   **Real-world Example:** Imagine telling a chef to stop cooking *all* current meals and clear their workspace before you hand them a completely new, updated menu for the day. You don't want them trying to cook and update the menu at the same time!
    *   **The Commands You'd Use:**
        ```bash
        sudo systemctl stop hospital-robot.service
        sudo systemctl stop robot-secure-mount.service
        ```
        *(You will be asked for your administrative password to run these commands.)*

*   **Step 2: Unlock the Recipe Book (Temporarily Mount Read-Write)**
    *   **Explanation:** Normally, the robot's main "recipe book" (its code storage) is locked and read-only. For an update, we use a special key (which is tied to the robot's unique hardware) to temporarily "unlock" this storage. Now, we can put new instructions inside.
    *   **Real-world Example:** This is like unlocking a secure vault or safe where you keep your most important documents. You only unlock it when you need to put new ones in or take old ones out, otherwise, it stays locked.
    *   **Important Note:** The "key" for this encryption is automatically generated by the robot's hardware. You don't need to type it; the command figures it out!
    *   **The Command You'd Use:**
        ```bash
        # First, define the special key command (this usually doesn't change)
        KEY_CMD='( cat /etc/machine-id; cat /proc/cpuinfo | grep Serial ) | sha256sum | cut -d" " -f1'

        # Then, use it to temporarily mount the secure code area
        sudo gocryptfs -extpass "$KEY_CMD" /opt/robot_secure_encrypted /opt/robot_secure_runtime/code
        ```

*   **Step 3: Replace the Old Recipe with the New One (Copy New Code)**
    *   **Explanation:** We take the carefully prepared new instructions (the updated code from our development team) and securely transfer them into the robot's unlocked storage. These new instructions replace the old ones.
    *   **Real-world Example:** You've made an improved version of a recipe card. You take out the old, slightly imperfect card from your recipe box and replace it with the brand new, perfected version.
    *   **The Command You'd Use:**
        ```bash
        # Make sure you are in the directory on your computer where your NEW, updated robot code is located.
        # Replace 'YOUR_NEW_CODE_SOURCE_DIRECTORY/' with the actual path to your updated code.
        sudo rsync -aHAX --numeric-ids YOUR_NEW_CODE_SOURCE_DIRECTORY/ /opt/robot_secure_runtime/code/
        ```
        *(This command efficiently copies only the changes, preserving permissions.)*

*   **Step 4: Lock the Book and Let the Robot Resume (Unmount and Restart)**
    *   **Explanation:** After we've copied the new instructions, we immediately "lock" the robot's storage again, making it read-only once more. Then, we tell the robot to start its tasks from the beginning. This time, it will use the new, updated instructions, always operating from a securely locked instruction set.
    *   **Real-world Example:** After putting the new documents into your vault, you lock it securely. Then, you tell the chef to resume cooking, knowing they are now using the new, updated menu, and no one can tamper with it while they work.
    *   **The Commands You'd Use:**
        ```bash
        # First, unmount the code area (lock the recipe book)
        sudo umount /opt/robot_secure_runtime/code

        # Then, restart the services to have the robot use the new code
        sudo systemctl start robot-secure-mount.service
        sudo systemctl start hospital-robot.service
        # Alternatively, you can simply reboot the entire system:
        # sudo reboot
        ```
        *(Rebooting ensures everything starts fresh with the new code.)*

**The Benefit:** This meticulous process ensures that the robot always runs on approved, tested instructions, and its core intelligence remains protected from any unauthorized changes.

## 3. Checking the Robot's Health and Data (Checking the Kitchen and Ingredients)

Not all parts of the robot are as strictly locked down as its main "recipe book." Some areas are for its daily operations, like a **kitchen's pantry for ingredients** or a **restaurant's logbook for daily orders and observations**. These areas are designed to be updated and accessed regularly.

*   **What we can check/maintain here:**
    *   **Logs:** The robot keeps a "logbook" of everything it does – like a pilot's flight recorder. We might need to check these logs to understand past events or clear them out if they get too full.
    *   **Runtime Data/Configuration:** Sometimes the robot needs a "scratchpad" for temporary information or settings that might change, like its operating hours or specific alert thresholds. These are stored separately.

*   **How we access these:**
    *   We can access these areas remotely using a secure connection, similar to how you securely log into your bank account online. This connection is called **SSH**, and it requires a **password** that only authorized personnel would know.
    *   **Real-world Example:** Imagine being a restaurant manager. You might remotely log into the restaurant's computer system to check the inventory (data), review the day's sales reports (logs), or update the daily specials (configuration), all protected by your manager password. You don't need to physically go into the kitchen vault to do this.
    *   **The Command You'd Use (from your maintenance computer):**
        ```bash
        ssh your_maintenance_username@robot_ip_address
        ```
        *Replace `your_maintenance_username` with the username you've set up on the robot for maintenance, and `robot_ip_address` with the robot's network address.*

**In essence:** While the robot's core intelligence is kept under very tight security, there's a clear and secure process for authorized people to give it new instructions or manage its operational data, ensuring both protection and practical use.
